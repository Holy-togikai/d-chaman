# 0002. 山ごはんを食べる時刻は持たない

- **状態**: 決定
- **決めた日**: 2026-11-18
- **決めた人**: Holy-togikai
- **関係するタスク**: T-004

## 何を決める必要があったか

山ごはんの機能を作ったとき、計画に持たせたのは「選んだレシピ」「作る人数」
「買い出しの進み具合」の3つでした。**食べる時刻は持っていません。**

そのため、ホーム画面の山ごはんのタイルだけ時刻が出ず、他の5段（出発・到着・登山・
下山・寄り道）と並びが揃っていませんでした。「ここにも時刻を入れるべきか」が宿題として
残り、T-004 として立てました。

## 選べた道

| 案 | 利点 | 欠点 |
|---|---|---|
| **A. 食べる時刻を持たせる** | 6段すべてに時刻が並び、見た目が揃う | **当たらない。** 山頂で食べるか途中で食べるかは、その日の天気と体調と進み具合で変わる |
| **B. 何も出さない（現状維持）** | 嘘をつかない | 調理にかかる時間が計画に入らず、下山が遅れる原因を見落とす |
| **C. 調理にかかる時間を出す** | 分かることだけを出す。休憩の見積もりに直結する | 時刻は揃わないままになる |

## 決めたこと

**C を採る。食べる時刻は持たず、調理にかかる時間を出す。**

## なぜそう決めたか

**当たらない時刻を出すと、当たる時刻まで信用されなくなるためです。**

このアプリが出す時刻（家を出る・歩き出す・下山の見込み）は、日の出日の入りの計算と
公表のコースタイムに裏打ちされています。そこに1つだけ根拠の薄い時刻が混じると、
利用者は画面全体を「だいたいの目安」として扱うようになります。
日没までに下山できるかという判断が甘くなるのは、このアプリでいちばん避けたいことです。

一方、**調理にかかる時間は分かります。** レシピごとに10〜30分と決まっており、
山で使えるバーナーはふつう1台なので、2品なら順番に作ることになります。

| 品数 | 調理時間 |
|---|---|
| 2品 | 45〜50分 |
| 3品 | 1時間を超える |

休憩の既定は1時間です。**2品作ると休憩のほとんどが調理で埋まり、3品なら超えます。**
これを見落とすと下山が遅れます。時刻より、この時間のほうが役に立ちます。

## この判断の結果どうなるか

### できるようになったこと

| 場所 | 表示 |
|---|---|
| ホームの山ごはんタイル | 「調理50分 ・ 買い出し1/11」 |
| 計画画面の時間割 | 「山ごはんの調理に35分。休憩の合計（1時間）に収まっています。」超えていれば橙で警告 |
| 山ごはんの画面 | 「選んだ2品を順に作ると、調理に35分かかります。」 |

- `HikePlan.cookingTime` は計算で出します。保存する項目は増やしていません
- **調理時間は休憩の合計に含まれます。** 別に足すと二重に数えることになります

### できないままのこと

- ホームの6段のうち、山ごはんだけ時刻が出ません。これは意図した状態です
- 「何時に食べるか」を計画に書き留めることはできません

### この判断を見直すとき

次のどれかが起きたら、作り直す価値があります。

- 利用者から「食べる時刻を決めておきたい」という声が複数出たとき。
  その場合も、**予測ではなく本人が入れる目標**として持たせるのが筋です
- 山行の記録から「実際に何時に食べたか」を集められるようになったとき。
  実績があれば予測が当たるようになります

## 根拠

- レシピの調理時間: `Apps/Yamatabi/Yamatabi/Resources/recipes.json`（10〜30分、12品）
- 休憩の既定値: `HikePlanner.defaultRestTime`（1時間）
- 制約としての記載: `docs/requirements.md`「山ごはんの時刻を持たない理由」
