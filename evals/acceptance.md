# acceptance.md — 検品のしかた

## 大原則

**AI の「できました」「動作確認しました」を合格理由にしてはいけません。**

AI は自分の仕事を良く見積もります。実際にこのプロジェクトで起きた例：

- 「挙動は変えていない」と書いたが、ルート選択が壊れていた
- 「ビルドが通った」が、見ていたのは古いフォルダの結果だった
- 「山を選べる」が、器具で絞り込むと候補が常に0件だった

どれも**画面を実際に見ていれば**防げました。証拠を見てください。

## 証拠として認めるもの

| 証拠 | 取り方 | 何を保証するか |
|---|---|---|
| ビルド結果 | `xcodebuild ... \| grep -E "error:\|BUILD"` | 文法と型が通ること。**動くことは保証しない** |
| SwiftLint | `swiftlint lint --quiet --config Apps/Yamatabi/.swiftlint.yml` | 書き方の決まりを守っていること |
| **画面写真** | シミュレータまたは実機 | **実際にそう見えること。いちばん強い証拠** |
| 具体的な数値 | 画面に出た値を書き写す | 計算が正しいこと |
| 実機への配置ログ | `xcrun devicectl device install app` の出力 | 実機に入ったこと |
| 外部データの実取得 | 件数と、取れた中身の例 | 通信と解析が動くこと |

## 証拠として認めないもの

- 「動作確認しました」「問題ありません」「正常に動いています」
- ビルドが通っただけ（**画面が白いままでもビルドは通ります**）
- コードを読んだ感想
- 「前回と同じやり方なので大丈夫」

## 仕事の種類ごとの検品

### 画面を変えたとき

1. ビルドが通る
2. SwiftLint が無警告
3. **その画面の写真**。変更前後で比べられるとなお良い
4. **触って確かめる**。ボタンが押せるか、遷移するか、戻れるか
5. 明るいところ・暗いところの両方（このアプリは常に白基調だが、念のため）

### 計算を変えたとき（時刻・距離・数量）

1. **具体的な数値を一つ以上**。「富士宮口で 前日22:57 出発 → 歩き出す 2:58 → 下山 15:46」
2. **端の場合**を試す。出発地が無いとき、コースタイムが0のとき、日付をまたぐとき
3. 可能なら**外部の値と照合**。日の出・日の入りは公表値と±1分で一致した実績がある

### 外部データを扱うとき

1. **実際に取れた件数と中身の例**。「富士宮口五合目の周辺15kmで15件。富士急雲上閣 6.4km ほか」
2. **取れなかったときの画面**。通信を切って試す
3. 出典の表示が出ていること

### データを生成するとき（Tools/ のスクリプト）

1. 生成されたファイルの**件数**
2. スクリプト内の検証が通ること（未定義の材料、単位のゆれ、ID重複など）
3. 既存のデータが壊れていないこと

## 検品役のふるまい

- **実行役の報告ではなく、証拠そのものを見る**
- 証拠が足りなければ、それだけで**不合格**。「たぶん大丈夫」で通さない
- 不合格にするときは、**何の証拠が足りないか**を具体的に書く
- 自分で直さない。直したくなったら、それは実行役の仕事

## 不合格の書き方

```
不合格。

passes の2番目「人数を変えると材料の量が変わる」について、証拠が
「確認しました」のみで、変更前後の数値がない。

次を出してください:
- 2人ぶんのときの玉ねぎの数量
- 4人ぶんに変えたときの同じ行の数量
- その2枚の画面写真
```
